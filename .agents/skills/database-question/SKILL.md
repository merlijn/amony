---
name: Database Question
description:
  Answer a developer's natural-language question about the Amony database by turning it into a SQL query, using the real
  database schema
---

Use this skill when a developer asks how to query the Amony database for something, for example "all resources added
after 2026-01-01" or "which users have the admin role". The goal is to produce a correct, index-friendly SQL query
grounded in the service's real schema.

If the question is not clear from the context (for example the skill was invoked without a concrete question), ask the
developer what they want to query before doing anything else.

## Workflow

### 1. Ensure the schema dump is present

The full database schema is produced by an sbt task that applies every Liquibase migration to a throwaway PostgreSQL
Testcontainer and dumps the result with `pg_dump --schema-only`.

- Check whether the dump already exists at `backend/target/amony-schema.sql`.
- If it is present, reuse it. Do **not** regenerate it on every question.
- If it is missing, generate it once by running, from the `backend` directory:

  ```sh
  sbt exportDatabaseSchema
  ```

  Notes:
  - This requires Docker to be running (it uses Testcontainers). Use the Java version defined in `backend/.sdkmanrc`
    (`java=25.0.2-tem`).
  - It takes a while (it boots a container and runs all migrations), so only run it when the dump is absent.
  - If it fails to pull images or connect, the developer may need Docker running or network access — stop and ask.

The migrations themselves live in `backend/src/main/resources/db` (the Liquibase changelog `00-changelog.yaml` plus the
numbered `.sql` files); the dump is generated by `nl.amony.ExportDatabaseSchema`.

### 2. Gather context from the schema

Read `backend/target/amony-schema.sql` (a `pg_dump --schema-only` output) to find the tables and columns relevant to the
question. It might be large, check the number of lines before deciding to either read it in full or search for relevant
information using grep.

For each table you use, note from the dump:

- Column names, types, and nullability from the `CREATE TABLE` statements.
- Foreign keys and how tables relate, from `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY`.
- Non-trivial column types so filters map to the correct expression, for example array columns such as
  `users.roles character varying(256)[]` or timestamp columns with `timestamp with time zone`. Confirm the exact type
  from the dump rather than assuming.

If the mapping from the question to a table/column is ambiguous, ask the developer a short clarifying question instead
of guessing.

### 3. Identify indexed fields

Before writing the query, build a list of what is actually indexed for the tables involved. In the dump, indexed columns
come from:

- `PRIMARY KEY` constraints (in `CREATE TABLE` or `ALTER TABLE`).
- `UNIQUE` constraints and `CREATE UNIQUE INDEX`.
- `CREATE INDEX` statements (note the column order for multi-column indexes and the type, e.g. GIN indexes for
  array/full-text/JSON search).

### 4. Write the query, preferring indexed fields

Produce a SQL query that answers the question and:

- Filters (`WHERE`), joins (`JOIN ... ON`), and sorts (`ORDER BY`) on indexed columns wherever possible.
- For a composite index, respects the leading-column rule (a filter that skips the leading column usually cannot use the
  index).
- Avoids patterns that defeat an index, such as wrapping an indexed column in a function, a leading-wildcard
  `LIKE '%x'`, or a type mismatch.

Follow these rules unless the user's question cannot be answered otherwise.

### 5. Warn about full table scans

If the query must filter or sort on a **non-indexed** column (or otherwise cannot use an available index), explicitly
warn that it may cause a full table scan, name the column(s) responsible, and when useful suggest one of:

- An existing index that would let the question be answered a bit differently.
- A more selective, index-backed predicate to add.
- A new index that would help (as a suggestion, not an action).

Always include this warning when the produced query is not index-backed; staying silent is worse than an unnecessary
warning.

## Output

Respond with:

1. The SQL query, in a `sql` code block.
2. A short note on which indexes it uses.
3. Any full-table-scan warning from step 5, if applicable.
